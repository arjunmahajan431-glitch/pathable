# Blockers and unverified items

Status checked: **2026-10-25**. This file distinguishes "not available in this
environment" from "not done by design."

## Blocking the real evaluation (student input required)

### 1. Whole-city coverage is not whole-city sidewalk knowledge

The app now covers **all of Woodbury** and **all of Saint Paul**, using OpenStreetMap
city boundary polygons and public landmarks as centers. The live OSM graphs and DEM
caches were downloaded for both cities, and the committed samples and screenshots use
those citywide extracts.

**Limitation:** mapping a whole city does not mean every sidewalk is mapped. OSM
completeness still varies block by block, and disconnected mapped components remain
possible. The app returns an honest `disconnected` or `no route` result instead of
inventing a connector. A citywide graph also cannot be inspected by hand the way a small
pilot extract could.

**What the student must do:** confirm that Woodbury and Saint Paul are the cities you
want to discuss. If not, edit `id`, `name`, `center`, `radius_m`, `boundary`, and
`is_placeholder: false`; run `make data`, `make elevation`, `make coverage`, and
`make evaluate`.

### 2. The field audit has not been collected

`data/fixtures/sample_field_audit.csv` is fabricated sample data. Its points now sit on
public sidewalk edges inside Woodbury so the importer and comparison code can be tested,
but it is not a finding. The Woodbury report labels every audit number as **SAMPLE DATA,
NOT A FINDING**. The Saint Paul report has no audit rows and says so. Neither invents a
result.

**What the student must do:** audit 10-20 public blocks in one of the two cities, record
the schema in `docs/FIELD_AUDIT.md`, import with `scripts/import_audit.py`, restart the
API, and rerun the evaluator. Report the sample size and the area it covers.

### 3. The repository path / remote was not supplied

The project lives in this workspace and can be committed locally. No remote URL, GitHub
account, or permission to push was provided, so nothing was pushed. That is consistent
with the brief ("commit locally only").

**What the student must do:** create/choose a repository, review the commit, and push
when ready. Never commit `.env` or an admin token.

## Capabilities that were unavailable or limited

### Browser test runtime

The suite now runs on this Windows machine with Playwright's bundled Chromium. On a
normal machine, `npx playwright install chromium` (or `make e2e-install`) installs the
browser. Linux hosts may also need their usual Chromium system libraries. If Chromium
cannot launch, the e2e suite cannot run; component tests and backend tests still can.

### Accessibility user testing

Automated axe checks pass with zero serious/critical violations, and a keyboard-only
Playwright flow passes. The app has **not** been tested by a wheelchair user, a screen
reader user, or an accessibility professional. Automated checks do not prove usability.

### Visual review

Screenshots are generated by Playwright and inspected in this workspace at desktop width
in light and dark mode, and at a phone-width Chromium viewport in light mode. A Playwright
test also checks the phone-width layout for sideways scrolling. The app has not been tested
on a physical phone, Safari, Firefox, or a high-contrast OS setting. The layout is
responsive by CSS, but those devices and browsers are unverified.

### Real-time conditions

There is no construction feed, live closure feed, or traffic data. Reports are
community-submitted and can be stale. The app does not claim otherwise.

## Not done by design (not blockers)

- No deployment, accounts, native app, indoor routing, transit, voice navigation, paid
  APIs, or external text-generation calls.
- No OSM edits from reports.
- No claim of accessibility, legality, medical suitability, or safety.
- No real audit photographs are committed; `photo_ref` is only a string.

## Remaining student checklist

1. Confirm Woodbury and Saint Paul are the cities you want, or set different public
   centers and boundaries and rerun the data/elevation steps.
2. Collect and import your own field audit for that area.
3. Run `make check`, `make e2e`, and `make evaluate` on your own computer.
4. Record the 1-3 minute public video; check the current rulebook.
5. Deploy only if you have a host and have reviewed CORS, tiles, and the admin token.
